# Local issue review for Capri 0.6.2

Investigation notes for the changes included in Capri 0.6.2. Verification entries describe development runs when each change was investigated, not a complete regression run of the final release. Final tests were deferred at the maintainer's request.

## Additional report — opening YouTube stops at window selection

**Cause:** two verified Chrome windows were open while another application was foreground. Native launch correctly returned `needsWindow: true` with `inputPerformed: false`; the task runner could select only a sole candidate or the currently observed window, so it stopped before any action. This was an application-window ambiguity, not a missing application ID or a network failure.

**Fix:** a launch-only request may activate the first native-verified application window when no candidate is foreground. Text entry still requires an unambiguous or currently observed window, and an explicitly requested window is preserved. For a requested website, the planner prefers direct official-page navigation instead of a preliminary browser launch.

The normal planner now returns a small task-local checklist alongside its first action. Checkpoints have observable success criteria; fresh screen evidence is required to mark an existing checkpoint complete. An ordinary blocking dialog, stale target or changed foreground can revise the remaining checklist without discarding completed work. A cookie banner interrupts navigation waiting immediately instead of waiting for the loading deadline. Already delivered navigation/search cannot be blindly replayed during recovery, including equivalent URL spellings or switching between search and URL actions. A confirmed network-error page can be retried. Direct website navigation also works without an existing controllable window; existing-tab input still requires an actual observation. Authentication, CAPTCHA and security barriers still require the owner; Esc cancellation, recovery budgets and independent final review remain enforced.

**Check:** open two Chrome windows, foreground another application and ask Capri to open YouTube. It should open the requested page without asking for an internal window ID. A request only to open YouTube ends there. Separately request a longer search-and-open sequence; test with an ordinary cookie dialog, a missing/stale target and a foreground switch. Confirm that recovery continues only the remaining requested work, optional cookies are not accepted unnecessarily, a typed URL alone is not reported as completion, and Esc stops recovery immediately. Ambiguous draft entry in a particular existing tab must still request clarification rather than type into an arbitrary window.

**Local verification:** 151 related regression tests cover checklist validation, revisions, fresh evidence, bounded failure recovery, multi-window launch, modal/cookie recovery, focus restoration, duplicate navigation prevention, and cancellation. `tools/verify/verify-application-window-choice.mjs` reproduces the genuine native multi-window result with disposable Windows applications and verifies exact-window activation without touching owner applications. `tools/verify/verify-computer-replanning.mjs` uses actual Windows text entry and clicks: a modal interrupts Save, native preflight rejects the stale action before input, and a revised plan dismisses the dialog and saves without typing again. Checklist labels, UI evidence and owner goals are never added to diagnostic traces; only counts are retained after a task.

An opt-in test against the selected Nemotron API produced the official YouTube URL, a checklist and the actual Reject all choice from synthetic observations. It also exposed a missing checkpoint-proof field in a premature completion proposal, which the host rejected. The completion schema and final prompt now explicitly require pending checkpoint proofs. Subsequent live model tests were blocked by provider HTTP 429, including a bounded delayed retry; full model end-to-end completion is not claimed. The verification uses synthetic observations only, preserves provider selection, and deletes its temporary encrypted Chromium metadata.

`tools/verify/verify-youtube-navigation.mjs` separately passed against the real public YouTube homepage in a disposable Chrome profile: one navigation dispatch, verified native address/title and visible homepage controls, one completed checkpoint, no pending work. This native execution check uses a deterministic driver rather than the rate-limited model. No cookie dialog appeared in that run; cookie/modal recovery is covered by the separate regression and native modal tests. It does not play videos or use account controls, and the temporary profile is removed after the test.

## #77 — application launch stops before its first action

[Issue #77](https://github.com/CapriChooms/Capri/issues/77) includes a 0.6.0 diagnostic snapshot. Full computer access is enabled, but the last task stopped in `observing` with `COMPUTER_APPLICATION_UNAVAILABLE` and zero completed steps. Runtime log tails were not included, so the exact foreground-window sequence on the reporter's PC cannot be reconstructed.

**Reproduced defect:** make the first native observation unavailable, then request an installed application by name. The runner previously required a controllable window before dispatching its pending launch. Consequently, even a valid launch could never happen when no suitable window was available. The regression tests fail against the previous implementation.

**Fix:** an unavailable initial observation can bootstrap a launch without manufacturing a usable input target. An exact owner-named application takes the existing verified catalog path; other languages can use the semantic planner, restricted to `launch` or `ask_user` while no real target exists. Clicking, typing, screen-based completion claims and other operations remain blocked until a fresh observation. Spanish imperative launch forms also use the direct path. If Windows does not verify the opened window, the runner requests owner help rather than replaying an uncertain launch. Transient read failures after an action get bounded observation retries; input is never automatically replayed.

**Check:** keep the same Full computer access grant enabled, request an application repeatedly, including after minimizing other applications. Try English, Russian and Spanish launch commands, then a chained launch-and-type request. Also cancel during launch and try ambiguous app names: no arbitrary click or false success should result. Native verification uses only a generated WinForms application, with a controlled unavailable-observation condition, actual catalog launch/focus verification and real text entry.

## #76 — 99% total system RAM with a large local model

[Issue #76](https://github.com/CapriChooms/Capri/issues/76) describes a modified 0.5.1 installation. It has no diagnostics, process-memory breakdown or model-offload counters. The reported 99% is total system RAM, not a measured allocation to Capri. A memory leak, CPU fallback, incomplete offload or duplicate resident allocations cannot be confirmed from that description alone.

**Local improvements:** clarify the requirements for a 16 GiB RAM / 16 GiB VRAM PC, and add `resources.json` to explicit diagnostic exports. It records bounded local-model allocation counters, whether the selected model reports CPU/partial/GPU residency, its context allocation, and aggregate working sets of Capri's owned processes. These are separate from total system RAM. Unknown counters stay unknown; no model is started to collect them. Model names, paths, digests, prompts and service errors are not exported by the new resource probe.

The local model counters use the read-only [Ollama running-models API](https://docs.ollama.com/api/ps). Their placement classification is an inference from its total and GPU allocation counters, not a measurement of peak process RAM. Shared process pages can also appear in more than one working set; the report states that limitation.

**Still needed:** reproduce the high-memory state on the affected installation and save a fresh diagnostic report. Compare `system.json`, `resources.json`, the selected context size and enabled speech components. Do not mark this issue resolved or claim a memory-consumption fix before that evidence exists.

## #75 — French voice download never begins

[Issue #75](https://github.com/CapriChooms/Capri/issues/75) contains the actual preflight error: its Radeon model is outside Capri's supported Windows ROCm voice list. Free disk space is sufficient; the download was deliberately stopped before starting an incompatible GPU runtime. Version 0.6.0 reduced this to an unhelpful generic installation message.

The current source already contains the 0.6.1 fix: preserve the specific unsupported-GPU reason and error code, and offer the compatible Qwen3-TTS CPU alternative where the selected language supports it. Repeated regression tests confirm that this happens before downloads, dependency commands or storage checks. This does not add unsupported ROCm hardware support, and CPU TTS performance is not guaranteed to be real time.

## Additional report — updating 0.5.1 to 0.6.0

The supplied diagnostic archive reports `Invalid source update manifest entry`, with accepted GitHub access and an attempted update from 0.5.1 to 0.6.0. The published source archive was identified by its GitHub SHA-256 and reproduced locally without starting an installation.

The 0.5.1 validator builds its expected inventory using the old release exporter's artwork catalogue. It omits seven `assets/capri/intro-v1/PNG/*.png` frames and `assets/capri/intro-v1/runtime-intro.json`, then rejects those eight legitimate manifest entries. Running that exact old inventory/validator against the published archive reproduces the reported error. The current validator accepts all 1,289 source files and checks their hashes independently of the installed artwork catalogue.

This fix is already present in 0.6.1 and retained locally for 0.6.2. An installed 0.5.1 client cannot acquire it through the source-update path that it rejects: use the full [0.6.1 installer](https://github.com/CapriChooms/Capri/releases/tag/v0.6.1) once, selecting the existing Capri folder. Do not uninstall or delete its data first. The existing updater regressions also verify fallback to a separately verified installer for genuinely unsupported future layouts, while malformed entries, unsafe paths and bad checksums remain hard failures.

All 29 updater, manifest-compatibility and installer-fallback tests passed again. No additional updater code change or new EXE was needed for this report.

## Workflow playback — false indicator startup error

**Reproduction:** enable Full computer access and replay a saved workflow from Settings without an active chat request. The real installed build reproduced `Computer control indicator did not become visible.`

**Cause:** the 400 ms main-process safety watchdog required an active chat turn, although workflow playback has its own owner-requested turn. It cancelled the session during indicator startup or before the first step. The startup handler then mislabeled cancellation as an indicator timeout.

**Fix:** supervision uses the same permission and owner-turn callbacks as the control runner, covering both chat tasks and explicitly started workflows. Permission revocation, owner-turn changes and loss of the Escape stop still end the session. Workflow cancellation now also aborts indicator startup immediately, and cancellation is distinct from an actual visibility timeout. The indicator must still become visible before any input.

**Verification:** the original installed source fails in the real Electron application; the patched source passes with the same isolated fixture and no active chat. Playback survives multiple watchdog ticks, and Stop clears the session and indicator. A second workflow completes all three harmless keyboard steps in the owned test application and closes its indicator afterwards. All 95 focused control, workflow, permission, identity, agent and desktop-boundary tests pass, including permission revocation, turn changes and emergency-stop availability. The installed source was patched separately with original-file backups; owner settings, memory and workflows were preserved. A running instance must restart to load these source changes. No installer was rebuilt or published.

## Home portrait — cropped face after a pose change or return

The home renderer previously centered only at startup, using the standing face position for every drawing. Pose changes retained the previous pan, and a button return did not commit its measured home placement. The bottom-aligned pan range also prevented exact face centering at some zoom levels.

The home camera now uses the existing authored face landmarks for each portrait/music pose and permits enough travel to center them without changing zoom or stretching the drawing. General pose changes retain the previous face position at the frame swap, then ease into the center over 320 ms. Mouth and expression frames do not restart this motion. Manual placement, zoom and dragging cancel camera recovery. Teleport return measures and commits the same centered destination for both button and drop returns, so the overlay and unfolding home frame agree. Reduced-motion mode centers immediately. The bounded animation has no idle polling.

Native screenshots were inspected for the centered face at maximum zoom. No new artwork, model calls, installer or published files are required.

## Voice worker ignores a restart requested during cold startup

## Unpublished follow-up — VAC rejected because devices share a group

The g diagnostic report from 0.6.2 describes **Use a call cable separate from your microphone** during virtual microphone setup. The snapshot has no connected call output and no synthesis attempt. The only source branch producing that warning compared the live input track's `groupId` with the selected output's group. A shared browser device group does not by itself establish that those endpoints form a feedback loop.

The archived report omits the chosen endpoints and groups, so their exact relationship on that computer cannot be reconstructed. Voice is also disabled in its final snapshot; enabling Capri's voice is separately required for speech after a successful cable connection. That setting does not explain the group warning.

The local follow-up keeps the conservative group rejection unless a fresh, bounded device inventory positively identifies a live physical microphone and one unambiguous VB-CABLE playback/recording pair, with distinct concrete endpoint IDs. Missing, stale, virtual or ambiguous input identities remain rejected. Validation runs before creating the call audio context. This does not disable feedback-loop protection or change sample rates, resampling, call volume or microphone ownership.

Setup diagnostics now retain only a bounded stage and failure classification, rather than raw endpoint IDs, names or exception text. The changes are not part of the already published 0.6.2 installer. Regression cases are included for later verification; tests, hardware capture and application runs remain deferred at the maintainer's request.
