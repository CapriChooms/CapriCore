# AMD monitoring and actual model placement

An unavailable VRAM graph was mistaken for CPU-only inference. The runtime
monitor queried only `nvidia-smi`, although the installer already discovered AMD
adapters with DXGI. On an RX 6400-class 4 GiB device, Ollama's actual Vulkan log
showed 17 of 25 language-model layers on the GPU. The separate embedding model
ran on CPU intentionally. Neither missing telemetry nor CPU embedding work proves
that the language model ignored the GPU.

## Fixes

- A shared, bounded Windows collector supplies AMD/Intel dedicated memory and
  GPU engine load using English PDH counters. Counter instances match the
  adapter's exact LUID. The busiest engine is measured without adding different
  parallel engines into a fictional percentage above 100. NVIDIA driver readings
  remain available.
- A missing memory counter preserves confirmed dedicated capacity and adapter
  name while leaving usage unknown. Shared UMA/system RAM is not reported as
  dedicated VRAM. Missing temperature is not replaced with zero or a guessed
  reading. Unknown samples cannot rearm a dismissed fullness warning as if real
  usage had returned to zero.
- The active Local choice shows `CPU`, `GPU`, `GPU + CPU` or `—` from the selected
  model's actual Ollama allocation counters. An empty inventory, unloaded model,
  embedding-only residency or failed probe is not labeled CPU-only inference.
- The status probe is a direct, bounded loopback `GET /api/ps`, with no proxy,
  credentials, redirects, model loading or generation. Cached/coalesced reads
  avoid extra work. API mode does not query a local conversation model.
- [AMD backend delivery and repair](0.6.4-amd-llm-runtime.md) additionally supplies
  the separately distributed ROCm package on supported local installations.

The native monitor is compiled once per reviewed source hash, shared between
requests and stopped after inactivity or a bounded failure. It does not spawn a
new PowerShell query for every displayed sample. Removing duplicate legacy
performance-counter initialization reduced the measured qualification worker's
private memory from about 79 MB to 57 MB; warm native samples took about 11–12 ms
on the qualification computer. These are collector measurements, not an AMD
inference speedup or a weak-PC guarantee.

## Verification

1. On Windows with an AMD adapter, open the resource graphs. Confirm the card's
   dedicated capacity and available real counters. A driver that does not expose
   a valid counter must leave that value unknown, not display `0%` or use shared
   system memory as VRAM.
2. Send a local request, wait for completion, then open the Local/API selector.
   Compare the active local allocation status with Ollama's resident inventory.
   Partial offload is valid on a small GPU; CPU use alone is not a failure.
3. Let the conversation model unload or leave only the CPU embedding model
   resident. The Local status must become unknown/unloaded, not claim CPU-only
   conversation inference. API mode must issue no local status request.
4. Repeat with missing/malformed counters, two adapters, shared UMA memory and a
   stopped collector. Stale readings must not be carried forward as current.
5. Check rings and graphs at compact and full widths. Tooltips retain the GPU's
   name and capacity when usage is unknown; missing temperatures remain unknown.

Focused tests cover those parser, lifecycle, residency and rendering conditions.
The compiled collector was exercised against a real NVIDIA driver without model
loads. Eight headless DOM scenarios used explicitly synthetic AMD readings;
they verify layout and semantics, not AMD driver operation. A real AMD retest is
still required before claiming compatibility with that card/driver combination.

## Limits

The reported high RAM percentage described the whole system, not Capri alone.
The reviewed report showed cold model loading, limited free RAM and mixed GPU/CPU
offload, but no demonstrated runner crash or out-of-memory error. A 4 GiB GPU
cannot be promised to hold every model, context and speech combination. Reduce
the selected model/context or use the existing API option when the workload
does not fit; do not force every model into GPU memory.

LLM acceleration, speech recognition and TTS have different hardware support.
RX 6400 is a Vulkan LLM candidate, not a promise of Chatterbox ROCm voice support.
No GPU-target spoofing, driver changes or forced unsupported backend is included
in this fix. See [Ollama hardware support](https://docs.ollama.com/gpu) for the
upstream backend requirements.
