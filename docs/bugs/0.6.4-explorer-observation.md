# Explorer observation fails on a missing UIA control type

During real-application verification, the production `computer_state` bridge failed while observing File Explorer. A private debug build reproduced the same failure and located it at the direct `current.ControlType.ProgrammaticName` access. The UI Automation result contained an absent managed control type; its name could not be dereferenced.

Native control-type naming now handles an absent type as an empty classification. The same helper covers observation, taskbar inspection, ancestor classification and catalogue output, so another absent type does not reintroduce the same failure elsewhere. Recognized control types keep their original names. Existing target validation, permission checks and input preflight remain active. The change does not catch arbitrary exceptions or claim that an action succeeded after a failed observation.

## Check

Bring File Explorer to the foreground and request an observation before issuing input. The old bridge failed on the affected window. The corrected production bridge observed that same window three times successfully, then observed a disposable QA folder and its synthetic text file. No owner file was edited, moved or deleted, and no raw UI labels were added to the verification report.

A separate native DLL regression checks absent and unregistered identifiers, plus unchanged Button, Edit, Document, Window and Custom classifications without opening or controlling a window. The real-application check demonstrates this affected Explorer case; it is not a guarantee for every accessibility provider or window state.
