# Discord: send to the visible chat pane

## Report and reproduced limitations

The report describes opening Discord and asking Capri to write a short message in the chat pane on the right, including the text chat attached to a voice channel. The app opened, but the message was not entered or sent.

The diagnostic archive contains one applied step and an unfinished plan. Its private action strings were omitted, so it cannot establish a particular native focus or mouse error. Production-function probes reproduced matching early-stop metadata and confirmed these host restrictions:

- Structured Discord requests required exact server/channel names and did not represent the already visible voice-channel text pane.
- A spatial phrase such as “on the right side” failed destination authorization, and an unquoted literal such as “hi” failed exact-message extraction.
- The planner could propose ordinary input that the Discord executor intentionally refused. Its private Discord projection did not expose the structural composer position needed to choose the requested pane.
- An early clarification could leave no terminal diagnostic reason. A second privacy pass also removed safe technical stop reasons.

Turning on passive screen observation does not resolve those routing restrictions. The fix does not enable Discord screenshots or expose unrelated conversations to the model.

## Implementation

A separate `send_current_message` action addresses a currently visible composer by `current`, `left` or `right`. It must match the original owner's instruction and exact message text. This is distinct from joining a voice channel or navigating to a named server/channel.

The native host identifies composer and message containers structurally and binds them to a content-free pane identifier. The executor checks fresh window/pane identity, preserves unrelated drafts, submits once and requires a new matching message together with an emptied owned draft in that pane. This verifies local submission, not network delivery. Ambiguity, a changed destination or an uncertain submission stops the task rather than guessing or repeating the message.

The model receives only bounded structural composer descriptors. Native pane identities, draft values, private fingerprints, visible message bodies and Discord images remain host-only. Existing named-channel operations keep their guards.

A bounded structural composer inventory skips message subtrees. A truncated message list is acceptable only when that inventory is complete and agrees with every exposed composer; an incomplete scan still stops. Native input checks the expected draft and pane again immediately before replacement or Enter. Discord launch has a bounded read-only readiness period, never a second launch or message retry after input begins.

Examples, hypothetical future instructions and typing-only requests do not authorize submission. These restrictions apply to both the direct path and model-proposed structured actions.

Terminal diagnostics retain fixed action, outcome and reason values while continuing to omit message text, destinations and identifiers. A clarification is recorded as `needs_user`, without inventing a crash.
