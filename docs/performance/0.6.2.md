# Backend performance measurements for 0.6.2

Only two established backend functions were refactored. Their visible behavior, limits and permission checks are retained.

| Function                                   | 0.6.1 median | 0.6.2 median | Speedup | CPU time reduction |
| ------------------------------------------ | -----------: | -----------: | ------: | -----------------: |
| Read and validate a 40-application catalog |    0.2289 ms |    0.1609 ms |   1.42× |              32.2% |
| Parse a 5,000-line SSE event               |   11.1872 ms |    0.7610 ms |  14.70× |              93.0% |

Catalog p95: 0.2982 → 0.2091 ms. SSE p95: 11.8501 → 1.2363 ms. CPU totals in the representative rounds: 484 → 328 ms for the catalog and 672 → 47 ms for SSE.

## What changed

`DesktopCatalog.apps()` reuses validated catalog rows only while file identity, size, modification time and change time remain unchanged. Every caller receives a fresh copy. Saving invalidates the cache. The file is still checked on each access; this is not a cache of permission decisions. Tests cover mutation of returned values and external permission changes, including restored modification times.

`ChatService.sseData()` counts accumulated data length incrementally instead of recounting every preceding line. It preserves the existing event limit, event-boundary reset and UTF-8 handling. This removes quadratic accumulation for unusually fragmented events; short ordinary events have a smaller absolute benefit.

## Method

Run `node tools/benchmarks/compare-backend-062.mjs` on Windows using Capri's supported Node version. The script loads the exact implementations from the clean 0.6.1 commit and the current source, warms both, alternates their order over three paired rounds in the same process and uses identical synthetic data. Catalog runs use 2,000 iterations per round; SSE uses 60. The comparison records median, p95 and CPU time in an ignored local JSON report.

The reference implementation is commit `1e4868a632d4765acd8cb297d3ed49e60b94799d`. Reported figures are local microbenchmarks and will vary with CPU, storage, caching and competing work. They do not imply a 14.7× improvement in model tokens per second, network latency or whole-application responsiveness. Heap/RSS snapshots are affected by garbage collection; no memory-reduction claim is made.

## Budgets for new features

- Brain indexes incrementally in a single background worker with a 128 MB V8 heap limit. It retrieves at most four bounded excerpts and never starts an embedding model.
- The compact composer and restore chip reuse their windows. The static chip has no cursor-polling loop. The idle dialogue-only presentation produced zero canvas draws in the native verification.
- Recording hooks enqueue bounded events and defer accessibility lookup to a worker. Recording stops after two minutes or 120 steps.
- Tool discovery never executes scripts. Tools run serially with a 256 MB process-memory limit, bounded CPU time/output and a maximum 60-second wall timeout. Context scripts share a three-second preparation budget, keyword filtering and an optional result cache.
- Reply auto-hide uses one timer rather than a permanent polling loop.

These are resource limits and behavioral checks, not fabricated before/after measurements for features that did not exist in 0.6.1.
