# Интеграция Hugging Face в Capri

План от 2026-11-04 для исходников v0.4.6. Первая реализация CAP-17 добавлена в локальный экспериментальный билд. Раздел ниже отделяет реализованное от дальнейшего расширения. Совместимость отдельной модели, языка и устройства требует своих проверок.

## Реализовано в локальном билде

- В Settings → Language model добавлены поиск Hub, просмотр лицензии и закреплённой ревизии, выбор GGUF/квантизации и projector, расчёт загрузки/свободного места/RAM/VRAM, докачка с проверкой контрольных сумм, отмена и удаление. Все части split GGUF разрешаются совместно. Токен необязателен для открытых моделей, хранится через системное шифрование и не пересылается на CDN.
- Подготовленная модель импортируется в управляемый Ollama. Проверяются шаблон диалога, поддержка completion и предел контекста; tools, vision и thinking включаются по фактическим возможностям движка. Пользователь применяет модель обычной кнопкой с сохранением памяти и настроек. Неподдержанная архитектура не становится активной. Для малых импортированных моделей доступны 8K/16K контекста.
- Wizard предлагает выбрать модель с Hugging Face после установки. Этот выбор пропускает фиксированную LLM и открывает библиотеку при первом запуске. Голос и распознавание остаются отдельными компонентами. В API-профилях добавлен Hugging Face Inference Providers.
- В Settings → Languages добавлен выбор модели голоса для каждого языка. Chatterbox Turbo использует английский адаптер Capri; Chatterbox Multilingual — проверенный образец Capri на 23 заявленных языках. Второе семейство Qwen3-TTS 0.6B Base имеет отдельный CPU runtime, закреплённые веса и десять заявленных языков. Его статус BETA не означает подтверждённое качество на всех языках.
- Для совместимого английского Chatterbox Turbo добавлена локальная кнопка дообучения на проверенных записях с расшифровками. Новый кандидат создаётся отдельно, его можно прослушать и применить. При неудачной проверке возвращается предыдущий профиль. Датасет и обученные пользовательские результаты не включаются в релиз или диагностику.

Произвольная модель TTS с Hub не получает автоматическую поддержку дообучения. Для каждого семейства нужен свой совместимый алгоритм. Qwen3-TTS и Chatterbox Multilingual используют обусловливание образцом голоса; это не обучение весов. Ни этот механизм, ни LoRA не гарантируют полного сходства с Capri на любом языке. Неподдержанные языки и семейства не обозначаются как готовые.

Проверены импорт реального GGUF и короткий локальный ответ через изолированный Ollama, модельные профили/откат, отмена и запоздалые ответы, контроль загрузок, защита путей/ссылок, изоляция токенов и установочный путь HF. Полная матрица устройств и оценка голоса носителями языка остаются отдельным этапом CAP-17F. Приведённые ниже архитектурные решения описывают и последующие этапы, включая Transformers, облачный TTS, расширенные фильтры и общую инвентаризацию всех семейств.

## Результат для пользователя

В Settings появляется библиотека языковых и голосовых моделей с поиском Hugging Face, фильтрами по языкам и оборудованию, установкой, проверкой, переключением, ремонтом и удалением. Добавление по ссылке или `owner/repository` использует тот же процесс. Для каждой модели видны источник, ревизия, выбранная квантизация, возможности, лицензия, объём загрузки, место на диске и оценки RAM/VRAM.

Пользователь отдельно выбирает LLM и TTS. Для каждого языка можно сохранить свою модель и голос, прослушать пример и увидеть статус проверки. Облачный Hugging Face оформляется как отдельный способ выполнения с явным выбором провайдера и передачи данных.

Поддержка определяется сочетанием модели, формата, адаптера, версии движка и устройства. Карточка сообщает конкретный статус — «Проверено в Capri», «Экспериментально», «Нужен другой движок» или «Недостаточно данных». Для неподдержанного формата объясняется, какой адаптер требуется.

## Архитектурные решения

### Общий каталог и идентичность модели

Добавить versioned descriptors в `packages/runtime` и общий разрешённый каталог в `config`. Существующие записи перевести в эту структуру с сохранением ID. На первом этапе достаточно файлов JSON и существующей атомарной записи.

| Часть записи   | Содержание                                                                                                                                 |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| Источник       | `source`, `repoId`, полный commit revision, выбранные относительные пути, размер и контрольная сумма с указанием алгоритма и происхождения |
| Выполнение     | Задача LLM/TTS, `backendId`, версия runtime profile, архитектура, формат, precision/quantization, совместимые устройства                   |
| Возможности    | Текст, изображения, tools, reasoning, контекст и предел ответа, языки, speaker/reference/adapter support                                   |
| Ресурсы        | Download bytes, installed bytes, peak staging bytes, RAM/VRAM и контекст измерения, отметка estimate/measured/unknown                      |
| Проверки       | Результаты и дата qualification для конкретной версии движка, языка и устройства                                                           |
| Лицензирование | Лицензии весов, движка, голоса и адаптера, attribution, gated access и сведения о разрешении распространения                               |

Разделить описание модели, факт установки и текущую активную конфигурацию. Receipt хранит проверенные файлы и результат подготовки. Статусы загрузки, установленности, готовности и нахождения в памяти должны быть различимы.

Метаданные Hub использовать для поиска и первоначального анализа. Каталог Capri добавляет проверенные ограничения. Для поиска доступны task, язык, автор, формат, параметры, лицензия и совместимость с устройством. Ввести пагинацию, debounce, отмену устаревших запросов, ограничение размера ответа и локальный кэш метаданных с датой актуальности. HF предоставляет поиск и фильтры через Hub API. [HF Search](https://huggingface.co/docs/huggingface_hub/guides/search)

### Единый план установки

`resolve → plan → download → verify → prepare → activate` становится общей последовательностью для Wizard, Settings и CLI. Расширить существующие ModelService/SpeechInstallService и их progress/cancel/recovery, сохранив одну точку применения конфигурации.

1. Разрешить repo ID и выбранную revision в полный commit. Зафиксировать файлы и зависимости в plan до начала установки. Изменение upstream branch создаёт новое предложение обновления.
2. Вычислить объём недостающих файлов, зависимостей и временного места. Учесть кэш, общие runtimes, копирование между дисками и свободное место на каждом используемом томе. Повторить проверку перед крупной записью.
3. Загружать в принадлежащий Capri staging с ограничением параллельности и сохранением частичных файлов. Показывать байты, скорость, этап проверки и возобновление. При отсутствии данных о скорости показывать состояние ожидания и время последнего прогресса.
4. Проверить обязательные файлы, затем атомарно зарегистрировать готовый пакет. Блокировка по пакету и журнал операций защищают параллельные install/repair/delete.
5. Подготовить новый пакет до смены активной конфигурации. При нехватке VRAM выгрузить текущую модель перед загрузкой новой, сохранив её пакет и профиль для восстановления. При неудаче сообщить результат rollback.
6. После перезапуска восстановить незавершённую операцию из журнала, проверить staging и предложить продолжение.

Hub поддерживает загрузку выбранных файлов по revision и предварительное получение размеров. Для GGUF использовать Node resolver/downloader в runtime, чтобы LLM-only установка обходилась без Python. Python SDK остаётся адаптером для TTS snapshots с тем же plan/receipt. Совместимость конкретной pinned версии SDK и Xet/HTTP проверяется отдельно. [HF Downloads](https://huggingface.co/docs/huggingface_hub/guides/download)

Для curated пакетов ожидаемые SHA-256 фиксируются при проверке каталога. При ручном импорте фиксировать commit, проверять доступный upstream digest с правильным алгоритмом и дополнительно считать локальный SHA-256. ETag обычного Git-файла может быть Git blob hash, поэтому сравнение всех ETag как SHA-256 ошибочно. Если независимой ожидаемой суммы нет, отражать ограниченную проверку в статусе. Текущий English receipt вычисляет хеши после скачивания, этот путь следует усилить. [HF File metadata](https://huggingface.co/docs/huggingface_hub/package_reference/file_download)

### Языковые модели

Первый рабочий путь — GGUF из HF, импортированный в текущий управляемый Ollama/native lifecycle. Прототип должен подтвердить поддержанный способ импорта выбранных файлов без обхода учёта процессов, residency и отката. HF документирует GGUF как формат для llama.cpp. [HF GGUF](https://huggingface.co/docs/hub/gguf-llamacpp)

- Для каждой модели проверять архитектуру, chat template, токенизацию, stop/EOS, context limit и generation defaults. Qwen-специфичные требования привязать к соответствующему adapter profile.
- Добавить capabilities gates в UI, OpenClaw configuration и action routing. Модель с подтверждённым текстовым диалогом получает отдельный chat-only режим. Автоматизация требует проверки tool calling, vision разрешается после проверки пары weights/projector.
- Проверять каждый shard и соответствие projector конкретной ревизии. Поддержку split GGUF включать после прогона на закреплённом backend. Если требуется слияние, включать выходной файл и временное место в plan.
- Контекст ограничивать минимумом реального лимита модели, движка, настройки пользователя и ресурсного бюджета. Текущий UI начинает выбор с 32K, внутренний минимум составляет 8K. Для диапазона 8K–<32K отдельно квалифицировать облегчённый диалог, селектор и бюджет инструкций. Модели ниже 8K получают понятный статус совместимости до разработки подходящего режима.
- Переключение между LLM пересчитывает контекст и возможности, сохраняет историю и отменяет предыдущий run. Проверять CAP-12A при длинной истории и CAP-12B при подключении памяти к облачному профилю.
- Второй адаптер для локальных Safetensors/Transformers вводить отдельным этапом. Он использует согласованный worker API, закреплённые зависимости и поддержанные архитектуры. Наличие Safetensors само по себе не подтверждает поддержку модели. Адаптер должен подключить chat, vision, readiness и residency к существующей защищённой inference boundary, заменив зависимость этих вызовов от Ollama API. Владение процессами и capability descriptor остаются общими для всех движков.

Начальный регрессионный набор включает текущую Qwen, одну текстовую instruction-модель другого семейства, одну tool-capable модель и одну vision-модель. Точные HF repositories, revision и quantization закрепляются по результатам прототипа и проверки лицензий. Это позволяет проверять разные контракты без произвольного расширения каталога.

### Голосовые адаптеры и языки

Ввести контракт `probe`, `prepare`, `synthesize`, `cancel`, `release`, `health`. Каждое семейство получает разрешённый адаптер и закреплённый runtime profile. Первым шагом обернуть текущие Turbo и Multilingual v3, сохранив их проверенный звук как регрессионную базу.

Контракт реализовать совместно с существующим CAP-06A. Его hardware providers отвечают за устройство и размещение token generation/audio decoder, CAP-17 добавляет семейства моделей, Hub artifacts и пользовательский выбор. Экспорт обученного голоса Capri в ONNX, DirectML и NPU остаётся отдельной аппаратной квалификацией CAP-06A. Kokoro представляет дополнительный голосовой вариант с собственными характеристиками.

Модель, speaker и Capri voice profile имеют отдельные идентификаторы. Выбор сохраняется по BCP-47 языку/диалекту с явной fallback policy. Подготовленный английский LoRA совместим со своей базовой моделью. Для другого семейства нужен совместимый профиль или отдельно проверенное reference conditioning.

- Убрать глобальное требование CUDA перед выбором движка. CPU/CUDA/ROCm/другие устройства объявляет и проверяет адаптер. Конфликтующие Python/Torch/phonemizer зависимости размещать в отдельных управляемых environments.
- Worker нормализует звук в существующий mono Float32 24 кГц, проверяет конечность значений, длительность, каналы и громкость. Это сохраняет контракт effects, subtitles и playback. Настоящий поток аудио вводится позднее через отдельную capability и версию протокола.
- Host health должен подтверждать активный backend, model revision и voice profile. Текущее требование идентичности Turbo распространить на реестр ожидаемых идентичностей.
- Предпрослушивание использует короткий локализованный тест, поддерживает отмену и отбрасывает запоздавшее аудио. Для remote TTS пользователь видит получателя текста.
- Каждый элемент очереди речи закрепляет run ID, backend, model revision, язык и voice profile. Смена голоса внутри одного языка отменяет прежнюю очередь и исключает воспроизведение старого результата.
- Смена языка использует уже загруженный совместимый backend. При смене семейства выполнять ограниченную транзакцию выгрузки/загрузки. Учитывать одновременную потребность LLM, TTS и ASR.
- В настройках доступны голос для каждого языка, «следовать языку разговора», явное разрешение определения языка и выбор поведения при отсутствии голоса. Состояние TTS при запуске и существующие переключатели загрузки остаются частью миграционных проверок.

Кандидаты для первого сравнения приведены ниже. Требования RAM/VRAM и качество речи будут измерены на закреплённых файлах и backend.

| Семейство                          | Роль в плане                                            | Языки и ограничения                                                                                                                                                 |
| ---------------------------------- | ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Chatterbox Turbo / Multilingual v3 | Первый adapter и регрессионный голос Capri              | Сохранить текущий English profile, затем квалифицировать русский и остальные выбранные языки. Upstream описывает multilingual семейство на 23 языках                |
| Kokoro-82M                         | Лёгкий CPU TTS pilot с готовыми голосами                | В официальном списке есть EN, JA, ZH, ES, FR, HI, IT, PT-BR. Русский требует другого пакета. Совместимость Windows и phonemizer входит в прототип                   |

Источник сведений о кандидатах — официальные карточки и документация. Поддержка в Capri подтверждается этапом qualification. [Chatterbox](https://huggingface.co/ResembleAI/chatterbox) · [Kokoro](https://huggingface.co/hexgrad/Kokoro-82M) · [Kokoro voices](https://huggingface.co/hexgrad/Kokoro-82M/blob/main/VOICES.md) · [Qwen3-TTS](https://github.com/QwenLM/Qwen3-TTS)

Языковой rollout предлагается начать с EN/RU, затем DE/FR/ES/PT/IT, далее JA/ZH/KO и остальных языков по наличию проверенного пакета и слушателей. Интерфейс, ASR и TTS имеют отдельные списки доступности. Кандидаты с дополнительными языками могут подключаться через тот же adapter contract после проверки.

### Облачный Hugging Face

В существующие API profiles добавить HF Inference Providers с endpoint `https://router.huggingface.co/v1`. Список для облачного запуска формировать по доступным provider mappings, контексту и возможностям. Hub repository и hosted service имеют отдельные статусы. Проверять соединение, текст, streaming, tools и vision независимо. [HF Chat API](https://huggingface.co/docs/inference-providers/tasks/chat-completion) · [HF provider mappings](https://huggingface.co/docs/inference-providers/hub-api)

Облачный TTS получает собственный адаптер через поддержанный HF inference client или пользовательский Inference Endpoint. Метод `text_to_speech` в SDK возвращает аудиобайты. Доступность конкретной модели, провайдера, языка и формата надо проверить запросом. Документация OpenAI-compatible endpoint ограничивает его chat completion задачами. [HF InferenceClient](https://huggingface.co/docs/huggingface_hub/en/package_reference/inference_client) · [HF routing](https://huggingface.co/docs/inference-providers/index)

Выбор local/cloud для LLM и TTS независим. Доступ к загрузке Hub и доступ к платному inference имеют отдельные разрешения. Текст, история, извлечённая память, изображения и reference audio передаются по настройкам выбранного профиля. Автоматическую смену облачного провайдера разрешать отдельной настройкой, поскольку меняются получатель и стоимость. Проверка доступности использует синтетический текст и ограниченный запрос. При 401/403, исчерпании бюджета, 429 и timeout выводить соответствующую причину.

LLM получает разрешённую для него историю, извлечённую память и изображения. TTS payload содержит только произносимый текст, параметры голоса и отдельно разрешённый reference audio. Локальные reference paths преобразуются в данные только после проверки выбранного voice profile и разрешения отправки.

### Настройки, Wizard и хранение

- В Models добавить вкладки «Языковые», «Голосовые», «Установленные», поиск HF и добавление по ссылке. Карточка показывает активную модель, языки, backend/device, совместимость и resource budget. Raw HTML карточек и внешние изображения автоматически не загружаются.
- В Languages разместить таблицу язык → модель → голос, тестовую фразу, preview и fallback. Панель памяти показывает сумму выбранных компонентов и текущий запас. Неизвестные оценки обозначаются явно.
- Wizard показывает рекомендованные пакеты и дополнительный каталог. API-only LLM исключает загрузку локальных LLM и их preload. Локальный TTS при облачной LLM выбирается отдельно. CPU TTS исключает ненужные CUDA зависимости.
- Общий install plan потребляют JS и PowerShell. Отдельно показывать download, постоянное место и пиковую потребность. Учитывать кэш и выбранную квантизацию, общий tokenizer/runtime считать один раз.
- Сохранять HF cache и receipts в принадлежащих Capri каталогах данных. Существующие Ollama/voice файлы сначала зарегистрировать и проверить на месте. Перенос на другой диск выполнять с проверкой копии и переключением указателя после завершения.
- Владельцы и ссылки на blobs определяют удаление. Показывать занимаемое и освобождаемое место отдельно, учитывать hardlinks и общие пакеты. Все сочетания удаления app/models/personal data проходят тесты. Токены относятся к personal data, частичные загрузки — к models/cache.

### Безопасность и приватность

1. Публичные загрузки выполняются без токена. Для gated/private ресурсов использовать отдельный fine-grained read token с зашифрованным хранением и возможностью удалить подключение. Gated разрешение пользователь получает у автора модели через HF. [HF tokens](https://huggingface.co/docs/hub/security-tokens) · [Gated models](https://huggingface.co/docs/hub/models-gated)
2. Реальные секреты доступны только доверенному main/download broker. UI после ввода получает masked status. Python workers получают артефакты или ограниченный транспорт через приватный IPC. Секреты исключаются из CLI arguments, постоянного environment, model prompts и публичной конфигурации.
3. Ввести отдельную Hub transport policy для API и официальных CDN/Xet redirects. Проверять HTTPS, hostname и адрес назначения на каждом переходе, снимать Authorization при переходе на другой origin, скрывать signed URL и query в ошибках. Сетевые ограничения сохраняются при retry.
4. Repo/file metadata, model cards и шаблоны считаются недоверенными. Валидировать размер manifest, количество файлов, Windows paths, ADS, `..`, абсолютные пути, ссылки/reparse points и архивы. Параметры процесса передавать структурированными аргументами.
5. Generic import разрешает форматы данных и адаптеры из приложения. Использовать `trust_remote_code=False`, reviewed template runtime и закреплённые зависимости. Команды README и Python код из модельного репозитория не входят в автоматическую установку.
6. Отдельно проверить существующие `.pt` loaders. Сохранить только рассмотренные загрузчики pinned legacy пакетов с безопасными настройками. Для ручного импорта исключить произвольную pickle-десериализацию. Принадлежность файла HF и результат сканирования учитываются вместе с собственными проверками. [HF Pickle security](https://huggingface.co/docs/hub/security-pickle)
7. Добавить синтетические HF-secret canaries в source export, installer diagnostics, desktop logs и ошибки streaming/download. Private repo IDs, signed URLs, voice references и local inventory исключить из публичных артефактов. Обнаруженный пробел regex экспортера требует теста и исправления до добавления авторизации.
8. Проверять лицензии конкретных revision весов, runtime и voice assets отдельно. Разрешение на распространение адаптера Capri и референса фиксируется в pack manifest. При переносе Chatterbox сохранить его встроенный watermark и применимые условия обработки аудио. Пользовательские записи и персональные voice profiles остаются в private data.

## Порядок внедрения

CAP-12A остаётся ближайшей P0 задачей. Проектирование CAP-17A можно вести параллельно. Полноценная qualification новых моделей требует корректных бюджетов контекста, отмены и измерений из CAP-12A. Работа CAP-12B продолжается отдельным этапом памяти.

Внутри D последовательность — обёртка Chatterbox, миграция настроек, выбор по языку, Kokoro CPU prototype, Qwen3-TTS prototype, сравнительное прослушивание EN/RU. Расширение выполняется после оценки зависимостей, памяти и качества каждого прототипа.

Первый поставляемый срез включает A–D и F для ограниченного набора public моделей. Следующий расширяет авторизацию, cloud и дополнительные архитектуры. Номер версии определяется после acceptance, отдельные этапы могут выходить experimental.

До прототипов зафиксировать измерения текущего Qwen + Chatterbox и тестовый набор без персональных данных. Для каждого кандидата сохранять публичный отчёт с model revision, runtime, обобщённым hardware profile, условиями и результатами. Предлагаемый regression gate для общего кода — ухудшение median/p95 warm latency базовых моделей не более 10% на одинаковом стенде. Для TTS с заявленной работой в реальном времени целевой real-time factor ≤ 1 на указанном устройстве. Остановка слышимого playback должна занимать ≤ 250 мс, освобождение зависшего worker ограничивается timeout. Пороги уточняются по повторяемости baseline до объявления модели поддержанной.

Расширить существующие тесты `model-selection`, `native-language-model`, `model-residency`, `model-pull-recovery`, `inference-api`, `context-policy`, `memory-budget`, `installer`, `installer-recovery`, `installer-diagnostics`, `source-release`, `language-settings`, `speech-install`, `voice-effects`, а также Python suites `model_download_test`, `voice_runtime_test`, `voice_compatibility_test`, `speech_language_test`. Новые тесты нужны для HF resolver/authorization, package transactions и adapter contracts.

Объявлять hardware/language combination проверенной после реального запуска и отчёта. CPU, NVIDIA и AMD требуют отдельных стендов. Intel/NPU имеют отдельные backend milestones, существующий локальный API путь Lemonade участвует в регрессии.

## Решения для первого прототипа

- Предпочтительный LLM путь — импорт проверенных GGUF в текущий Ollama/native lifecycle. Подтвердить импорт split files и projector на закреплённой версии.
- Предпочтительный простой TTS pilot — Kokoro CPU. Многоязычный reference-conditioned кандидат — Qwen3-TTS, сравниваемый с текущим Chatterbox. Windows wheels, phonemizers и качество определяют включение в каталог.
- Предпочтительное хранение — owned package inventory поверх существующих каталогов, затем управляемый общий cache. Миграция по возможности регистрирует уже имеющиеся файлы.
- Открытые вопросы — точные HF revisions/quantizations, параметры языковых packs, доступные cloud TTS providers, согласованные latency targets и результаты физических AMD/Intel/NPU тестов. Они закрываются в прототипах и qualification.

Готовность первой интеграции означает, что пользователь проходит весь путь от поиска до диалога и речи, может прервать установку, сменить модель, восстановиться после ошибки и удалить выбранные пакеты. Доступность дополнительных моделей растёт через проверенные adapters и capability records.
