# Native NPU, Windows compatibility, coding mode and task progress

Технический план от 10 ноября 2026 года. База: локальная Capri 1.0.5,
коммит `6542fae`. Работа ведётся локально, без публикации релиза и изменения
пользовательской установки на Z. Номер следующего релиза этим планом не меняется.

## 0. Состояние и общие правила

- Desktop: Electron 45, Node 24.22.1, OpenClaw 2026.10.6; локальная генерация
  обслуживается управляемым Ollama/llama.cpp. Начальные точки:
  `packages/runtime/src/providers/services.mjs`, `apps/desktop/main.mjs`,
  `apps/desktop/inference-api.mjs` и `apps/desktop/chat-service.mjs`.
- Выбор CPU/GPU уже разделён для языка и голоса: `model-device-settings.mjs`,
  `hardware/model-devices.mjs`, `apps/desktop/model-device-service.mjs`.
  Поддержка NPU сейчас ограничена внешним loopback API Lemonade.
- `ComputerAgent` выполняет до 100 решений; `ComputerTaskPlan` хранит до восьми
  крупных контрольных этапов, их проверку и ограниченное перепланирование.
  Успешная отправка ввода сама по себе не доказывает выполнение этапа.
- `ControlOverlay` уже создаёт прозрачное окно на каждом мониторе, проверяет
  видимость индикатора и останавливает управление при потере индикатора.
- Инструменты идут через `ActionBroker`/`CompanionActions` и локальные интеграции.
  Coding станет отдельным разрешением, а не разновидностью Full computer access.
- Сохранить отключённую по умолчанию загрузку микрофона/голоса, выбор API,
  историю, память, горячий Escape и раздельное управление моделями.
- Не писать тексты запросов, содержимое файлов, пути личных проектов, подписи
  этапов и секреты в общие логи/диагностику. В измерениях — только коды, числа,
  длительности и разрешённые ID моделей.

## 1. Встроенный NPU

### Runtime и форматы

1. Добавить `integrations/npu/worker.py`: собственный дочерний процесс Capri,
   ограниченный JSONL-протокол `probe`, `load`, `generate`, `unload`, `shutdown`.
   Результаты и токены идут по приватному stdio, стороннее приложение и API-ключ
   не нужны. Пользовательские URL серверов для этого режима не используются.
2. Адаптер Intel: `openvino_genai.LLMPipeline(modelPath, "NPU", config)`.
   Использовать согласованный набор OpenVINO/Tokenizers/GenAI 2026.4, отдельное
   окружение и подготовленные IR-модели, а не пытаться открыть GGUF на NPU.
3. Адаптер AMD/Qualcomm: прямой `onnxruntime_genai` из совместимого официального
   vendor runtime. `Model` → `Tokenizer` → `GeneratorParams` → `Generator`,
   инкрементальная декодировка. Принять только модель с нужным EP и реально
   обнаруженным NPU. DirectML и CPU не выдавать за NPU; hybrid отмечать отдельно.
   Не подменять NPU режимом API к запущенному Lemonade.
4. Детектор проверяет SDK, архитектуру, ОС, драйвер и доступное устройство;
   наличие названия NPU в PnP недостаточно для `available=true`. Неподдерживаемая
   комбинация остаётся видимой с конкретной причиной и рабочим выбором CPU/GPU.
5. Добавить manifest модели: backend, ID, локальный каталог, поддержка шаблона
   чата/изображений/инструментов, предел контекста. Веса, IR/ONNX и токенизатор —
   данные; загрузка удалённого Python-кода запрещена. Проверять ссылки и выход
   внешних tensor/ONNX-файлов за границы каталога модели.

### Подключение к Capri

6. Новый `packages/runtime/src/providers/npu-service.mjs` владеет процессом,
   очередью, лимитами вывода, тайм-аутами, отменой и освобождением модели.
   Отмена не ждёт окончания длинной генерации: cooperative stop, затем
   принудительное завершение только собственного worker при превышении срока.
7. Внутренний совместимый transport (`/api/chat`, `/api/generate`, `/api/show`,
   `/api/ps`, `/v1/chat/completions`) нужен существующим компонентам Capri.
   Это внутренняя граница процесса, не пользовательская настройка внешнего API.
   Использовать приватные stdin/stdout дочернего процесса (не открывать порт), не журналировать
   тела. Потоки, finish reason и cancel должны совпадать с действующим контрактом.
8. Выбор backend вынести в общий resolver. `rt.inferenceUrl`, ID и capabilities
   должны указывать на выбранную модель. Ollama оставить для embeddings, если
   они используются; его разговорную модель при NPU не загружать.
9. Расширить сохранённые language-device настройки и Model devices; голосовой
   NPU не объявлять поддержанным без отдельного голосового адаптера. Добавить
   выбор/импорт подготовленной NPU-модели в Language model и установку runtime
   как необязательного компонента. CPU/GPU/API остаются доступными.
10. Для текстовых NPU-моделей сохранить минимальный диалоговый путь, существующую
    память и проверку JSON-планов. Не объявлять tools/vision по имени модели:
    неподдерживаемые возможности явно отключаются.

### Проверка

- Контракт worker: сбой импорта, отсутствие NPU, несовместимый EP, неверные
  каталоги, ограничение вывода, отмена, повторный запуск, unload и закрытие.
- Реальные загрузка/поток OpenVINO на доступном устройстве; тест CPU адаптера
  отмечать как CPU, не как подтверждение NPU. Реальный NPU throughput возможен
  только при наличии подходящего NPU на этом компьютере.
- Переключения API → NPU → GPU/CPU без потери истории и двойной загрузки LLM.
- Подтверждённые производителями ограничения ОС показывать отдельно от общего
  минимума Capri. Современный NPU SDK не делает старую Windows совместимой с NPU.

## 2. Старые Windows 10

1. Аудит импортов/версий поставляемых Node/Electron/Ollama и нативных helpers.
   Проверить реальные места вызова новых Win32/WinRT API; сборка установщика
   и отсутствие искусственного build-check ещё не доказывают совместимость.
2. Новый общий `packages/runtime/src/hardware/windows-capabilities.mjs`:
   версия/build/архитектура → доступность базового запуска, WGC, media sessions,
   уведомлений и NPU. Критичные функции дополнительно пробуют реальный API.
3. Первичная цель — Windows 10 1809/LTSC 2019 (17763), включая 1909 и LTSC 2021.
   Проверить возможность дальнейшего снижения до 1607/1507 по реальным импортам
   и доступной тестовой ОС; не объявлять неподтверждённый минимум поддержанным.
   Если обязательный бинарник требует более новой сборки, сохраняется его
   фактический минимум, а причина фиксируется в отчёте.
4. Разделить общий минимум и минимумы компонентов в `config/installer.json`.
   Исправить `packages/installer/windows/worker.ps1` и соответствующие UI-проверки:
   одно правило для install/update/repair, без устаревшей строки «22H2 required».
5. Вместо вызова отсутствующего API: WGC → доступный desktop capture путь;
   новые DPI-функции → проверенные Win32 альтернативы; toast → страница Finish
   и flash taskbar. Spotify/другие WinRT возможности, которым нет честной
   альтернативы, отключать с объяснением, не обрушая приложение.
6. Поддержку старой ОС не реализовывать откатом на неподдерживаемый старый
   Electron/Node или выключением sandbox/TLS. Обновить документацию минимумов.

Проверки: границы 10240/14393/17763/18363/19044/19045/22000/22621,
отсутствующие функции, чистая установка/repair/update, запуск app и helpers.
Отдельно записать настоящие VM/ОС-прогоны и проверки с подставленным build:
вторые проверяют политику, но не заменяют запуск на старой Windows.

## 3. Coding mode и прямой доступ к редакторам

### Отдельная возможность

1. Новая интеграция `integrations/coding/`: manifest/tool `coding_control`,
   `service.mjs` (typed actions), `workspace-policy.mjs`, `editor-catalog.mjs`,
   адаптеры CLI и необязательный мост VS Code. Разрешение выключено по умолчанию.
2. Пользователь выбирает корень проекта и редактор; права чтения, правки и
   запуска проектных задач независимы. Запретить обход scope через `..`,
   symlink/junction, UNC/device path и внешние tensor/скриптовые ссылки.
3. Действия: `status`, `list_files`, `read_file`, `search`, `open_file`,
   `apply_patch`, `diagnostics`, `list_tasks`, `run_task`, `cancel_task`.
   Ограничить размер/число файлов, текстовый вывод и время. Чтение больших
   проектов постраничное; поиск ограничен проектом и игнорирует binaries,
   `.git`, зависимости и секретные файлы по умолчанию.
4. Правки — атомарные, с hash исходной версии и понятным diff. При конкурентном
   изменении редактором не перезаписывать его текст; перечитать и перепланировать.
   Отменять только собственные изменения, не `git reset --hard`.
5. Запускать только явно разрешённые проектные задачи. `execFile`/argv/cwd без
   shell-интерполяции; дополнительное подтверждение для нового исполняемого
   задания. Не наследовать ключи Capri, HF/LLM-токены и приватные env.
6. Добавить инструмент в companion broker, OpenClaw config и tool-domain routing.
   В coding mode предоставлять только нужные coding/memory-инструменты и контекст
   проекта, не включать desktop_control. Результат подтверждается реальными
   файлами, диагностикой и exit code, а не заявлением модели.

### Редакторы

- VS Code, Insiders, Cursor, Windsurf: их обнаруженные executables и штатный
  `--goto file:line:column`. Не путать запуск .cmd через shell с прямым CLI.
- JetBrains (IDEA, PyCharm, WebStorm, Rider и другие): обнаруженный launcher,
  документированные аргументы открытия файла/строки.
- Visual Studio: `devenv /Edit` и поддерживаемые параметры перехода.
- Sublime Text и Notepad++: штатные файловые CLI с числовой строкой/столбцом.
- Neovim: явно выбранный server/GUI, только безопасно экранированные команды
  открытия. Для других редакторов — выбранный exe и проверенный шаблон argv.
- Общие чтение/правки/сборка работают на файлах проекта независимо от редактора.
  Получение живого выделения, несохранённого буфера и IDE diagnostics требует
  специального моста; не обещать эти функции только на основании наличия CLI.
  Для семейства VS Code подготовить расширение с приватным локальным мостом и
  явным Workspace Trust; не открывать unauthenticated HTTP listener.

### Интерфейс и тесты

Кнопка Coding mode в строке ввода, видимое имя проекта, отдельная вкладка Coding
в Settings, выбор папки/редактора, список разрешённых задач, состояние исполнения
и Cancel. Пояснить передачу выбранного кода внешней модели при API режиме.

Проверить реальный небольшой JS/Python-проект в установленных редакторах:
найти ошибку → прочитать → исправить → запустить тест → подтвердить результат.
Отдельно: конфликт правок, секретные файлы, обход путей, запрет shell/env,
зависшая задача, отмена, работа без Full computer access и с выключенным grant.

## 4. Цепочка этапов управления компьютером

1. `ComputerTaskPlan` получит отдельное UI-представление (ID, label, completed,
   remaining, revision); `diagnostics()` по-прежнему возвращает только счётчики.
2. `ComputerAgent` публикует актуальную цепочку после принятия нового плана и
   подтверждения checkpoint. Только host-verified checkpoint становится зелёным.
   Старт задачи показывает подготовку, blocked/stop/failure — своё состояние.
3. `main.mjs` пересылает план в `ControlOverlay`, включая первый план до появления
   окна и повторное подключение renderer. Не добавлять названия этапов в audit.
4. Новый небольшой renderer/controller в `control-overlay` строит keyed DOM.
   Горизонтальный flex-контейнер закреплён сверху по центру монитора. Активный
   этап — мягкий scan/glow, будущие — приглушённые, подтверждённый — зелёная
   галочка, короткая выдержка, затем исчезновение и сжатие.
5. Изменения порядка и количества — FLIP/Web Animations (transform/opacity),
   постоянное центрирование всей цепочки. Объединять быстрые обновления, не
   создавать JS-таймер на каждый блок. Длинные подписи ограничены; максимум
   крупных checkpoint остаётся ограниченным, микро-действия не засоряют экран.
6. Уважать reduced motion, выбранную тему, DPI и маленькие экраны. Панель не
   перехватывает мышь и не меняет фокус; Escape и подтверждение видимости рамки
   остаются в действующем нативном механизме. При нескольких мониторах не
   перекрывать содержимое центральной области и не терять индикатор управления.

Проверки: первая загрузка, рост/сжатие, reorder, замена остатка, несколько
одновременно завершённых этапов, завершение/ошибка/отмена, новые задачи подряд,
повторные события, 100 обновлений, RTL, reduced motion, малый экран и DPI.
Визуально проверить реальные Electron окна и записать короткое превью анимаций.

## 5. Реальные сценарии и повышение надёжности

Матрица моделей: доступная сильная API-модель, доступная средняя локальная и
самая маленькая установленная локальная. Не скачивать несколько десятков GB
только ради названия модели. Фиксировать точный ID, backend, результат, шаги,
время, повторные попытки и отмену; содержимое личных окон не включать в отчёт.

1. Браузер: открыть YouTube, обработать возможный cookie/modal, искать через
   поиск сайта, выбрать нужный из похожих результатов, проверить страницу видео,
   включить/остановить и полноэкранный режим. Не подтверждать подписки/платежи.
2. Между приложениями: браузер → редактор → Проводник → обратно; Unicode,
   сочетания клавиш, копирование/вставка и drag/drop на собственных тестовых
   файлах. Не считать набранный, но не отправленный URL завершённой навигацией.
3. Discord: найти приложение/сервер/канал и перейти. Отправку теста проверять
   только в специально выбранном безопасном месте, не в случайном настоящем чате.
4. Steam: обнаружить библиотеку, запустить установленную игру, проверить окно и
   вернуться. Не менять покупки, сохранения и пользовательские настройки игр.
5. DaVinci Resolve: отдельный QA-проект и созданные тестовые клипы; импорт двух
   клипов → сборка таймлайна → разрез/склейка → простой титр/переход → сохранение
   и короткий экспорт → проверка файла/длительности. Личные проекты не трогать.
6. Ошибки: закрытое окно, изменившийся заголовок, устаревший target, задержка
   открытия, modal/cookie, смена foreground пользователем, пропавший элемент,
   модель с плохим JSON и Escape во время каждого длительного этапа.

Исправления выбирать по наблюдаемой причине: переобнаружение окна вместо
угадывания appId, новое наблюдение после смены окна, проверка фокуса до ввода,
подтверждение отправки и навигации, точная привязка похожих целей по окружению,
безопасное перепланирование оставшихся этапов. Не повторять неопределённую
мутацию и не делать бесконечный цикл «до успеха».

«Любая задача без ошибок» не является доказуемой гарантией для произвольного
приложения/модели. Критерий сдачи: все заявленные сценарии реально пройдены на
доступной матрице, воспроизводимые критические сбои устранены, ограничения
не скрыты; оставшиеся аппаратные/OS-прогоны перечислены отдельно.

## Первичные технические источники

- [OpenVINO GenAI on NPU](https://docs.openvino.ai/2026/openvino-workflow-generative/inference-with-genai/inference-with-genai-on-npu.html): прямой LLMPipeline, особенности подготовки и исполнения NPU.
- [OpenVINO requirements](https://docs.openvino.ai/2026/about-openvino/release-notes-openvino/system-requirements.html): ограничения ОС/драйвера; это не требования всей Capri.
- [AMD direct Python/OGA flow](https://ryzenai.docs.amd.com/en/latest/llm/high_level_python.html): runtime и модель должны соответствовать поддерживаемому Ryzen AI стеку.
- [Node 24.22.1 build/support policy](https://github.com/nodejs/node/blob/v24.22.1/BUILDING.md): проверять именно поставляемую версию runtime.
- [Electron platform changes](https://www.electronjs.org/docs/latest/breaking-changes/): сохранять поддерживаемый renderer и capability fallback вместо старого небезопасного runtime.
