# Capri 1.0.5 qualification

This records the local release preparation, not a claim that every hardware,
driver and paid provider combination has been tested.

The prepared installer also includes the subsequent [memory-estimate calibration](../performance/memory-estimates.md), verified with real 32K model and voice measurements and native/runtime budget parity.

## Fixes found during qualification

1. **Recovery from a tiny quota.** Competing GPU work could push the model's CPU
   submission quota to its minimum. Zero utilization samples and integer
   rounding then prevented recovery when that work ended. A regression first
   reproduced the failure; the controller now recovers even from zero readings.
2. **Live slider changes.** Changing the target discarded calibration. Lowering
   it could temporarily increase the CPU budget and GPU load. Retargeting now
   preserves calibration and scales the existing quota immediately. A regression
   reproduces the old behavior; continuous real generation also exercises the fix.
3. **Runner replacement.** GPU associations are rebuilt when owned runner
   membership changes, including replacement with a CPU runner. A previous
   runner's GPU counters no longer influence the new cohort.
4. **Proactive replies.** The desktop activity gate now includes active
   initiative generation as well as user replies, click reactions and startup.
   Optional local comments can no longer bypass the limiter solely because no
   user request is in progress.

## Real local-model generation

An isolated loopback Ollama service used an already cached Qwen3.5 2B model,
4K context, fixed prompts and seeds, and stock hardware settings. No owner
conversation, external API, power limit or clock change was involved. Samples
were collected after startup stabilization, with a GPU thermal stop at 78°C.

GPU figures use Windows' busiest associated WDDM engine, not NVML's utilization
measure. Ten-second averages include controller transients; GPU targets are
approximate and brief peaks are permitted. These are throughput characters, not
tokens. CPU accounting intervals and Windows CPU-cycle quotas also differ
slightly. All native applied CPU quotas stayed within the selected ceiling.

Continuous generation additionally checks live/rapid target changes, disabling
and re-enabling control, forced helper termination/recovery, and release when
local activity ends. Repeated turns reuse one named job, avoiding stacked quotas.

## Regression and interface checks

- Full JavaScript baseline: 1,877 passes, three explicit skips, no failures;
  extended load-control tests are run again after the fixes.
- Native checks: wrong supervisor creation time is rejected; actual CPU quota
  application, command-lease expiry, clean stop, host reset, forced helper exit
  and repeated turns release or restore quotas correctly.
- Actual Electron UI/IPC: Local menu defaults, persistence, enable/disable,
  slider keyboard controls, English/Russian layout; optional external TTS,
  supported AI-provider UI, roaming, and memory-warning shortcuts.
- Interface language verification: all 50 supported languages, including
  preservation across restart and changes while a reply is in progress.
- Release checks include source/credential boundary validation, native wizard
  rendering, compiled installer extraction, source/voice manifests and hashes.

External TTS and ChatGPT connection transport/error handling use controlled
loopback fixtures, not paid provider accounts. Physical AMD/Intel GPUs,
multi-GPU configurations and a fresh multi-GB dependency download on another
Windows machine remain separate qualification work. Review the installer on
the intended test machine before worldwide publication.

### ChatGPT setup follow-up

OAuth regressions exercise an actual loopback callback with an unresolved Windows
browser-launch promise, cancellation during that launch, and a sanitized launch
failure. Completion and cancel no longer wait for the OS launch promise. Existing
PKCE, identity, consent, encrypted storage and refresh protections remain covered.

The actual Electron settings verifier exercises automatic model discovery after
sign-in, slow/failed/empty lists and retries, account switching with a stale prior
response, selection preservation, a fresh Settings renderer using a saved account,
and a single explicit **Use connection** call through the existing switch handler.
Sign-in itself never invokes provider switching. Accounts, models and inference
results are synthetic; live account entitlement is not asserted by these checks.

The catalog-size regression first reproduced the reported error with a rich model
list above 512 KiB. Catalog reads now have a separate 8 MiB budget and at most
4,096 entries; token and JWKS packets keep their 512 KiB limit. Oversized streams
are cancelled, a refresh can recover, and malformed/hidden rows are excluded.
Electron UI verification now runs the real production catalog parser over a
Chromium loopback fetch with 130 visible models and large metadata, instead of
returning pre-parsed model choices from the IPC fixture. Only model IDs and display
names reach the picker; provider metadata and bearer credentials do not.

The connection-test failure was reproduced against the selected GPT-6.1 Terra
account route: HTTP 200, no Content-Type, valid SSE and response.completed with the
fixed Ready. sample. The corrected production adapter completed the same fixed
probe in about 2.1 seconds. No conversation history was sent or token refreshed;
only status/type/count/timing metadata was recorded. Response text, account identity
and bearer credentials were not logged. Account eligibility and provider behavior can vary.

A missing media type now permits bounded SSE parsing, while explicit non-SSE
media types, malformed content, failed/incomplete responses and streams missing
response.completed still fail. Regression tests cover buffered connection probes,
streaming replies, cancellation, body cleanup and network-error classification.
The actual Electron Test connection button also uses the production adapter over
a headerless Chromium loopback response, rather than a synthetic success flag.

### Installer model selection follow-up

The native Hardware page is also checked as an update, using disposable install
metadata with a current model that differs from its stale resource profile.
The picker stays enabled, marks installed/current entries, defaults to the actual
model, retains a changed selection on navigation, and includes local Hugging Face
imports. Installed import receipts and artifact sizes are revalidated by the worker;
unknown imported memory use is shown as `?` rather than a catalog estimate.

Transaction regressions confirm that a different catalog model is selected before
its download, ports/context remain intact, and interruption restores the previous
model. Keeping the same choice leaves local/gateway settings byte-identical. API
and deferred-import updates do not change the saved local model. Synthetic fixture
transports avoid multi-GB downloads; native rendering exercises the real controls.

### Setup completion notice

Completion notifications are gated on a successful worker exit and a complete
event, after all events have been read. A native fixture drives success, failure,
cancellation and a complete event followed by worker failure through the real
wizard poller. Success announces once; the other cases never announce success.
Fixture runs suppress actual desktop alerts. Production uses the standard Windows
tray notification with localized completion text and version, taskbar attention
without taking focus, click-to-open and bounded icon/timer cleanup.

### Update startup recovery

Both native Capri.exe and the runtime launcher now distinguish a terminal update
journal from an interrupted installation. A matching schema/transaction ID and
`complete` or `rolled-back` phase permit startup only after the installer has
exited. Missing, malformed, oversized or linked journal paths, mismatched receipts,
nonterminal phases and live/invalid installer locks remain blocked. Startup does
not remove receipts or change installed files; cleanup stays with the updater.

Regression checks exercise the compiled native launcher's actual decision method,
the runtime decision and the desktop entry point, alongside updater commit,
rollback, retry and interrupted-transaction tests. No diagnostic ZIP was available
for the French download-failure report, so the original download failure remains
unconfirmed; this correction addresses the independently reproduced stale-receipt
startup block, not an assumed network cause.

### Qwen installation (issue #20)

The reported sequence (select Qwen3-TTS, download) reproduced a deterministic
failure in the production installer: its sanitized environment omitted PATHEXT.
Windows PowerShell then treated the Python executable as a document launch,
returning a Process object instead of its version text, with no native exit code.
The correct installed Python was consequently rejected as the wrong version.
The child now receives a fixed COM/EXE/BAT/CMD extension list; inherited API keys,
HF tokens and Python path overrides remain excluded.

A fresh disposable Qwen environment installed its actual pinned dependency set,
verified every model artifact, and reached Ready through VoiceCatalogService and
the owned PowerShell worker. Cached model bytes were reused and their pinned hashes
rechecked; a live fetch of the small pinned model config also matched its hash.
The installed CPU runtime generated a nonempty finite 24 kHz Russian greeting
(0.96 seconds of audio); no audio was played into calls or speakers. This host's
roughly 9.6-second cold load and 6.5-second generation are smoke-test measurements,
not a performance guarantee on the reporter's hardware.

Native regression coverage runs the real Python bootstrap under the service's
restricted environment. Failure checks cover installer lock release and preserve
only fixed reason codes, stages and exit codes through the full diagnostic ZIP
privacy passes. Raw subprocess output, paths and credential canaries are absent.
The old report did not retain the Qwen failure, so that user's exact original
exception cannot be confirmed retrospectively.

### Terra image capability and ordinary-reply regression

The supplied report and the current installed settings reproduced a mismatch:
the ChatGPT connection stored vision=false, while diagnostics showed the local
Gemma capability list beside the active Terra ID. The ChatGPT creation path had
hardcoded false. Capability resolution now keeps only safe catalog flags and
reviewed exact IDs. Legacy automatic settings resolve Terra as image-capable;
catalog results and explicit manual disabling remain respected. Model permission
resolution does not capture a screen or send an image by itself.

The current local timing log (which the exported ZIP had truncated away) showed
about 1.55 seconds in intent classification, followed by a gateway dispatch and
no visible reply before the 30-second first-text deadline. Responses conversion
had discarded the off/none setting, leaving Terra's provider reasoning default
active. Ordinary chat and auxiliary classification now explicitly use none for
Terra, retain the requested 64-token classifier budget, and send its JSON schema.
Owner-enabled deep thinking still forwards medium. Models without reviewed none
support use low instead. This corrects the identified request-policy defect;
the old trace does not prove which private upstream operation consumed each second.

Regression coverage runs the real multilingual classifier through the HTTP API
proxy and Responses conversion, including image input, streaming text, explicit
thinking, terminal response validation and controller cleanup. Diagnostic export
also keeps the most recent 500 records, so a later failure remains available.
An additional live-account probe was skipped because its stored access token had
expired; no credential refresh or account change was performed by that probe.
Computer Use could not initialize to run the app's own connection test. A new
fixed-sample check through the user's account is still needed after rebuilding.

### Voice API setup usability

The real Electron settings window was checked with a disposable local speech
endpoint and a short, quiet synthetic sample. Fresh setup keeps local voice as
the default and blocks cloud activation without a successful test. One Save and
test action commits encrypted settings before testing; a failed save retains the
draft and never tests stale values. Editing a voice, changing provider, retrying
HTTP 401, removing a connection and returning to local voice were exercised.
Changing provider does not reuse a key from another origin. Switching cloud off
preserves unsaved fields; the encrypted key never appears in the saved JSON.

All 50 interface catalogs pass completeness, placeholder, numeric and script
validation. The actual English, Russian, German, French, Arabic and Japanese
windows were inspected, including inline errors and action layout. Russian copy
was written directly; cloud-voice terminology was also corrected in German,
French and Spanish. Native proofreading of the other translations remains welcome.
The 15 external-TTS backend tests pass. These checks validate UI and transport
behavior; they do not confirm a paid provider account or its network availability.

Run `node tools/verify/verify-external-tts.mjs` to repeat this check. Reports and
screenshots are saved under the ignored `.runtime/desktop-verification` folder.

### Spotify planning through ChatGPT

The supplied diagnostic stopped in `spotify-planning` after about 1.65 seconds,
before model/context preparation, a gateway dispatch or a Spotify action. The
active provider was ChatGPT with `gpt-6-luna`. The request used a root `anyOf`
schema, which violates the Responses [object-root requirement](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=responses).
The reproduction through the real ChatService, planner, authenticated local HTTP
proxy and Responses conversion produced the same empty failed turn when a test
endpoint enforced that requirement. The diagnostic did not retain the upstream
error body, so its precise historical HTTP response cannot be recovered.

The proxy now nests the original union under one `result` property and unwraps
exactly that envelope before the existing planner validation. Ordinary object
schemas and native local inference remain unchanged. Extra root fields, unknown
command fields, out-of-range volume, malformed JSON, cancellation and non-music
verdicts still fail closed. Failed preflight never falls back to a desktop action
or retries a Spotify mutation. Safe failure codes and HTTP status now survive
in the response diagnostics; provider bodies and private request text do not.

The six relevant suites pass 151 tests, including Luna/Terra request conversion,
English/Russian commands and French planner output. An additional check ran the
fixed public request through a synthetic Responses endpoint and the real installed
Spotify bridge: one plan, one resume command and verified playback. The original
playback state was restored; the owner's conversation was not modified. A live
cloud probe was skipped because its saved access token had expired by verification
time; that token was still valid at the reported request time. No sign-in refresh
or credential changes were performed.

## Repeat the local load check

Use the release's Node runtime and explicit paths to a cached Ollama/model set:

```powershell
node tools/verify/verify-local-model-load-real.mjs --ollama="C:\TestRuntime\ollama.exe" --models="C:\TestModels" --model=qwen3.5:2b --duration=10
```

Use `--suite=live` to repeat just the continuous-generation scenarios. Reports
stay in the ignored `.runtime/local-load-real` directory. They contain numeric
measurements and test outcomes, not prompts, API keys or owner history. Public
test prompts are defined in the verification script.
